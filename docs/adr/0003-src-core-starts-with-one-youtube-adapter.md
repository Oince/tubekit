# `src/core/`는 YouTube 페이지·플레이어 어댑터 하나로 시작하고, 페이지 변경 알림은 넣지 않는다

기능마다 YouTube에 같은 질문을 따로 묻던 코드를 `src/core/youtube.js` 하나로 모은다. 묻던 것은 어느 화면인지, 지금 영상이 무엇인지, 플레이어가 어디 있는지, 광고 중인지였고, 기능마다 답이 이미 어긋나 있었다. 영상 화면 판정은 주소에 `v`가 있는지를 보느냐 마느냐로 갈렸고, 광고 판정은 상태 표시 두 개를 다 보느냐 하나만 보느냐로 갈렸으며, 떠 있는 영상 페이지를 찾는 규칙도 두 벌이었다. 어댑터는 이 판정 규칙과 YouTube 플레이어 메서드 호출 전부를 숨긴다. 플레이어 메서드가 없거나 예외를 던져도 기능이 멈추지 않게 감싸는 일까지 어댑터가 한다. 그래서 기능 모듈은 플레이어 메서드를 직접 부르지 않는다. 1~3줄짜리 도우미만 옮기는 얕은 core는 지워도 잃는 것이 없으므로 만들지 않았다.

"지금 영상"(GLOSSARY)도 어댑터가 하나로 정한다. 영상 화면이면 주소의 영상이고, 그 밖에서는 광고 중이 아닐 때 플레이어가 틀고 있는 영상이다. 주소가 먼저 바뀌고 페이지와 플레이어는 뒤따라오므로, 어댑터는 "페이지가 따라왔나"와 "플레이어가 따라왔나"도 함께 답한다. 기능은 자기에게 필요한 쪽만 확인한다. 어댑터는 상태를 기억하지 않는다. 기억을 어댑터에 두면 한 기능이 부른 일로 다른 기능이 받는 답이 바뀌는 길이 생기기 때문이다. 미니플레이어로 따라가는 플레이어 같은 기억은 각 기능이 가진다.

"페이지·영상이 바뀌었다"는 알림을 대신 받아 나눠 주는 일은 어댑터에 넣지 않았다. 기능마다 원하는 순간이 다르다. 쇼츠는 이동하기 직전에 목적지를 바꿔치기하고, 댓글 패널은 이동이 시작되자마자 걷어 낸 뒤 변화를 모아 다시 판단한다. 회전은 플레이어가 영상을 불러오는 즉시, 화질은 재생이 시작될 때 반응한다. 이것을 한 통로로 합치면 YouTube 알림에 이름만 다시 붙이는 얇은 층이 된다. 또 기능들이 알림을 받는 순서와 시점이 바뀔 수 있는데, 그 차이는 화면에 바로 드러나지만 jsdom 테스트로는 막기 어렵다.

## Considered Options

- **공용 질문만 어댑터에 두고, 한 기능만 쓰는 플레이어 조작(비율 키워드, 화질 설정)은 기능에 남기기**: "두 기능 이상이 쓸 때만 core" 규칙을 글자 그대로 지킨다. 하지만 플레이어 내부 호출과 예외 처리가 기능 곳곳에 남아 YouTube와의 경계가 흐려진다. 그래서 규칙을 모듈 단위로 따지기로 고쳤다(AGENTS.md).
- **페이지 변경 알림 통로까지 core에 넣기**: YouTube가 알림 이름을 바꿀 때 한 곳만 고치면 된다. 하지만 위 이유로 미뤘다. 두 기능이 정확히 같은 순간을 원하게 되면 다시 따진다.
- **테스트에서 어댑터를 가짜로 바꿔 끼우기**: 기능 테스트는 단순해진다. 하지만 어댑터가 숨기는 YouTube 해석(광고 표시, 주소 해석, 예외 처리)이 기능 테스트에서 빠진다. 그래서 가짜는 YouTube 플레이어 쪽(`fakePlayer`)에 한 벌만 두고, 어댑터는 실제 코드로 기능 테스트를 지나가게 했다.

## Consequences

- 새 기능이 YouTube 플레이어나 화면 판정이 필요하면 어댑터에 묻는다. 어댑터에 없는 판정이 필요하면 기능에 새로 짜지 말고 어댑터에 더한다.
- 어댑터의 판정을 바꾸면 그것을 쓰는 모든 기능의 동작이 함께 바뀐다. 광고 판정을 합칠 때 화질 쪽 판정이 넓어진 것이 그 예다. 실제 YouTube에서는 두 광고 표시가 함께 붙고 떨어져 화면 차이는 관찰되지 않았다.
- 페이지 변경 알림 구독은 기능마다 남아 있으므로, YouTube가 알림 이름을 바꾸면 기능 여러 곳을 고쳐야 한다.
- 회전이 YouTube에 배치를 다시 계산시키려고 보내는 신호(`requestLayout`)를 댓글 패널도 받아 다시 잰다. 이 결합은 `test/main.test.js`가 지킨다.
