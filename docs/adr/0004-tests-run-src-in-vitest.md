# 테스트는 배포물이 아니라 `src/`를 Vitest에서 시험하고, 기능은 테스트 전용 정리 함수를 돌려준다

회귀 테스트는 빌드된 `tubekit.user.js`를 jsdom 창에 `eval`하지 않고, Vitest(jsdom 환경)에서 `src/`의 기능 모듈을 직접 불러와 하나씩 시작해 시험한다. 배포물을 `eval`하던 때는 확인할 수 없는 것을 볼 때마다 번들 속 함수 이름을 문자열로 바꿔 끼워야 했고(`function evaluate() {`, `function redirectTo(url) {`), 이름이 바뀌면 테스트가 깨지는 대신 아무것도 확인하지 않고 통과했다. 또 기능 4개가 한 창에서 함께 돌아 한 기능의 테스트가 다른 기능의 내부 이름을 알아야 했고, 시간은 내부 상수에 맞춘 `sleep()`으로 기다렸다. `build.test`가 이미 "커밋된 배포물 = `src/` 빌드 결과"를 보장하고 빌드가 `minify: false`라, 배포물에서만 생길 위험은 작고 Chrome MCP 브라우저 검증이 배포물을 그대로 주입해 덮는다.

Vitest의 jsdom 환경은 테스트 파일마다 창 하나를 쓰므로, 테스트마다 모듈을 새로 불러오면 앞 테스트가 `window`·`document`에 붙인 리스너와 observer가 남아 두 벌이 돈다. 그래서 각 기능의 `start()`는 그 리스너와 observer를 떼는 정리 함수를 돌려준다. 이 함수는 테스트만 부르고 `main.js`는 반환값을 버린다. 사용자가 기능을 켜고 끄는 수단이 아니므로 "기능 켜기/끄기를 두지 않는다" 규칙과 어긋나지 않는다.

## Considered Options

- **배포물을 계속 `eval`하고 문자열 치환마다 존재 확인만 붙이기**: 비용이 가장 적지만 빈 테스트만 막고, 기능 사이 간섭과 `sleep`은 남는다.
- **기능별 IIFE 번들을 테스트 때 만들어 테스트마다 새 jsdom 창에 `eval`**: 창이 테스트마다 새로 생겨 정리 함수가 필요 없지만, 이 방식만의 빌드 단계와 도구를 따로 유지해야 한다.
- **`node:test`에서 전역을 jsdom 창으로 바꿔치기하고 `import`**: Node와 jsdom 환경이 섞이고, 함께 불러온 모듈이 캐시에 남는다.

## Consequences

- 배포물을 실행해 보는 자동 테스트는 없다. 번들러가 실행 시점에 무언가를 깨뜨리면 브라우저 검증에서만 드러난다.
- 정리 함수가 리스너나 observer를 빠뜨리면 다음 테스트에 남은 것이 섞여 돌고, 테스트가 끝난 뒤 생긴 오류는 통과로 묻힐 수 있다. 새 리스너·observer를 붙일 때는 정리 함수에도 넣는다.
- jsdom이 가로챌 수 없는 동작(`location.replace` 같은 페이지 이동)은 기능 폴더 안의 별도 파일로 떼어 `vi.mock`으로 바꿔 끼운다.
